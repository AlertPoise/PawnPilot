# PawnPilot wire v2 contract

Frozen M2-B implementation contract. Wire version is 2; journal format is independently 2. Production write allowlist contains **close_menu only**. No reflection, arbitrary methods, scripts, trading or inventory writes. Test verifiers are dependency-injected in managed tests, never enabled by config/environment/wire action names.

## Snapshot

Keep the v1 flat identity/lifecycle fields to minimize migration: schema_version, version, world_epoch, revision, phase, scene, loaded, ready, not_ready_reason, cash, menu_open, can_close_menu. schema_version=2; version equals world_epoch:revision. IDs/epochs <=128 chars, versions <=256, reasons <=512. Integers are strict (not bool), nonnegative revision <=2147483647; cash signed Int32. Add required fields:

- interaction: {phase: string<=128, consistency: consistent|updating|unverified|blocked, reason: string<=256|null, operable: bool}. operable means the supported base UI/lifecycle is ready, not that economic actions or all windows are legal. Current game business consistency is **unverified**; menu close has its own ready/menu predicate. Unknown full UI ordering is not certified consistent. Future verifiers must assert all action-specific predicates, not N stable frames alone.
- business: {support: "unsupported", customer_ref:null, item_refs:null, offer_ref:null, collection_fingerprint:null}. Null item_refs means not implemented, not empty stock.
- legal_actions: array (max1) of {action:"close_menu",arguments:{}} supplied by game on the same captured snapshot; must exactly agree with can_close_menu. Broker only adds connection/epoch/version/single-writer gates; Adapter projects game actions.

Execution is separate from game-state revision/signature (otherwise accepting a command would invalidate its own expected revision). Broker /state adds execution: progress|null alongside its existing envelope keys (schema_version now 2). Progress is also queried with command status. Game state changes, not wall time/progress, advance revision. Future M2-C must include business membership/quote/UI changes.

## Request, parameters and deadlines

/commands exact keys: schema_version,id,broker_epoch,action,expected_world_epoch,expected_revision,expected_version,arguments. v1 rejected explicitly schema_version_unsupported. All unknown keys rejected. arguments is an object with only optional customer_ref, item_refs, offer_ref, collection_fingerprint, option_ref. Ref strings 1..128 ASCII [A-Za-z0-9_.:-]; collection_fingerprint 1..128 same syntax; item_refs 1..64 unique refs, ordered list (order is semantic). No null values or nested arbitrary objects. Missing vs present is semantic. close_menu requires {}. Contract support for collections does not authorize any economic action. Validate generic parameter shape and fingerprint before comparing existing ID; different well-formed args on same ID -> command_id_conflict even though new close_menu args would be rejected.

Canonical request fingerprint = SHA256 of UTF-8 JSON with sorted object keys, compact separators, ensure_ascii=True, no NaN; preserve arrays. Covers every exact request key. C# may cache a length-prefixed canonical envelope string for equality, including all arguments + deadlines, but shared fixtures must test request canonicalization/fingerprint. Strict JSON depth <=16, body <=65536; duplicate JSON keys rejected.

Future reference lifetime: refs are opaque, Bridge-issued decision-snapshot handles, never persistent database IDs. M2-C must bind each customer/item/option handle to the current Mod session, world epoch and revision. A collection fingerprint must cover the complete ordered item_refs and relevant ownership/location; an offer_ref must bind that collection, customer, terms/amount/currency and the same decision identity. Any membership, ownership, quote, selection/UI condition or world/session change invalidates the handles and offer together by advancing revision/identity. A client cannot salvage an old offer by substituting one item or recomputing a hash. The Bridge must verify the complete binding again immediately before invocation. M2-B issues no such handles and accepts none for its only action.

Delivered Command adds start_deadline_unix_ms (broker now + start TTL default5000) and execution_timeout_ms (default5000, range1..30000). No expires_at_unix_ms in v2. start deadline checked immediately before invocation. Execution deadline is fixed when invocation starts: monotonic elapsed timer locally plus reported Unix started_at + timeout; wall clock changes must not extend local execution. Heartbeat timeout default3000 is independent. Delivered but no invocation evidence past start deadline -> unknown, not safely expired. Invocation evidence doesn't authorize indefinite progress: deadline never extends. Pending not delivered past start -> rejected. Any delivered disconnect -> unknown. A valid retained result may resolve broker unknown, never replay.

## Progress, results and exchange

Progress exact fields: id,broker_epoch,stage,sequence,may_have_side_effects,started_at_unix_ms,execution_deadline_unix_ms. stage=validated|invoking|verifying|completed|uncertain; sequence positive monotonic Int32. validated => effects=false,timestamps=null. invoking/verifying => effects=true,timestamps nonnull. completed can effects=false for rejection or true for success; uncertain true after invocation. Broker synthetic unknown may have no progress (delivery uncertainty). started/deadline immutable across a command; deadline=started+execution_timeout_ms; started<start_deadline. Duplicate sequence must have identical content; regression/conflict rejected. Progress may skip stages between heartbeats; only monotonic permitted forward transitions. Native-call flag is conservative, set BEFORE invocation.

Exchange exact keys: schema_version,session_id,broker_epoch,state,has_result,result,progress. progress null or above. has_result required bool; false keeps old explicit-flag behavior (ignore default result object). Result exact keys: schema_version,id,broker_epoch,status,reason,before,after,execution. status uses only succeeded|rejected|outcome_unknown (legacy failed only historical). execution is terminal Progress or null for broker-generated non-game results; Mod must provide terminal progress. Rejected must prove not invoked (effects=false); succeeded must have completed/effects=true and valid action-specific before/after. For close_menu, same world/scene, ready before/after, before.can_close_menu, after.menu_open=false, revision increases, cash unchanged. Invoked exception/timeout/world change => unknown. Result snapshots are immutable copies.

Reply remains schema_version,broker_epoch,acknowledged_result_id,has_command,command. Persist result before ACK. Mod retains/retries result until exact ACK. ACK reclaims heavy snapshots but preserves ID/fingerprint tombstones; unknown ACK does NOT release write lease. Success/rejection may release after ACK (no indefinite wait for later Agent dialogue). New command after terminal ACK routes through the same executor. Broker epoch change while validated rejects before invoking; after invoking becomes unknown, retaining old epoch evidence. No production synchronous bypass.

Internal stages are separate from external pending|running|succeeded|rejected|failed(history)|outcome_unknown. running means delivered and possibly invoked. Broker command reply keeps id,command_status,status,result,resolved,resolution and adds schema_version=2,execution:progress|null,record_schema_version:1|2. status is canonical in v2; legacy historical result retains its original schema/status. GET result can return original wire1 evidence in a v2 envelope with record_schema_version=1; never relabel old evidence v2.

## Storage and recovery

Journal v2 top level {journal_format_version:2,broker_epoch,records}. New records retain existing fields and add execution:null|progress. v1 records keep original requests/commands/fingerprints/results (including status aliases); detect using command.schema_version. Preserve strict v1 validator. Migration first validates complete old file, writes fsynced sibling .v1.bak without overwrite (existing backup must match), validates v2 candidate, then atomic replaces using existing durable save. Any failure preserves original; interruption backup is idempotent. No record eviction. Same 4096 records/16MiB limits fail closed.

Restart pending -> rejected, running -> unknown; unresolved unknown remains blocked across repeated restart. Preserve original epoch/ID/schema when synthesizing historic result. V1 wire is never accepted from a Mod; old unresolved close_menu requires controlled manual alignment after old Mod has exited (no v1 late result submission). Keep manual reconciliation restricted to close_menu, no MCP clear-unknown. V2 reconciliation must additionally prove execution can no longer invoke: require fresh different Mod session for delivered unknown (and original latest possible execution deadline elapsed). C# unknown gate intentionally stays blocked until operator-reviewed Mod restart. Store original command deadline in existing resolution field command_expires_at_unix_ms, now max(start_deadline+execution_timeout); schema_version of resolution identifies current wire snapshot version. Do not generalize this recovery to future economic actions.

## Read-only wait and verification

wait_for_update criterion=revision|command_terminal|operable, max_wait_ms 0..30000. revision requires observed broker_epoch/world_epoch/revision and wakes on any identity change; command_terminal requires command_id (unknown is terminal but still write-blocking); operable requires connected fresh snapshot, ready, interaction.operable and broker can_act. It never asserts trade legality. Exactly relevant criterion parameters; unknown keys rejected. Poll <=250ms; absolute monotonic deadline covers the whole wait, including streamed HTTP bodies and both GETs for command status; cancellation stops future polls and submits nothing. Zero means one immediate observation attempt, with a combined network budget of at most 50ms and no polling sleep. Result structured with outcome updated|terminal|operable|timed_out and latest snapshot/command status. Errors distinguish protocol/config/connection/business. No retry of POST commands. MCP schema_version argument to act required Literal[2] plus exact integer validation, so v1 clients get an explicit incompatibility rather than silently upgraded requests.

Testing: preserve previous cases, adapt their v2 fixtures without deleting risk coverage. Simulation source explicitly fixture; test multiframe driver via the same production close_menu dispatcher + injected native/verifier only in tests. Never export a test action in production. Economic effect completion and subsequent needs_agent/animation must be independently represented by verifier completion vs interaction phase.

Deadline boundary clarification: now >= deadline is expired (start and execution). Mod that proves it never invoked returns rejected/completed/effects=false even if broker has already conservatively marked its unconfirmed delivery unknown; do not invent invocation timestamps. A previous invoking/verifying report forbids such a rejection.

Mod-side ACK tombstones retain the full request fingerprint and original terminal status, not snapshot object graphs. An impossible redelivery after ACK is locally refused as already acknowledged without posting a second conflicting terminal result. Normal same-ID query/retry returns the original durable broker record. Unacknowledged duplicate delivery returns the retained immutable evidence and never invokes again.

The broker journal retains complete immutable results/snapshots for historical query and duplicate-result ACK verification. Only the Mod memory reclaims those snapshots after ACK. Journal record/byte limits fail closed rather than prune dedupe evidence.

Epoch cancellation uses the latest broker epoch actually received by the Mod. A broker can restart between delivery and the next exchange; the Mod cannot know that restart immediately. The replacement broker never redelivers that command and conservatively records delivered work as unknown. This is not a distributed exactly-once guarantee.
